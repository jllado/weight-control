# Task 536: Copy a full nutrition day
## Approved behavior
Dashboard New meal uses the dashboard selected date as immutable target. Before choosing a meal type, offer latest 14 distinct earlier dates containing meals, newest first. Whole-day copy only when target has no meals. Each day option matches the meal selector: bold first recorded food + N remaining foods across all meals, date below left and total kcal right (No foods for totals-only days). Existing single-meal options retain latest14 matching earlier entries and gain kcal.
Selecting a day deep-copies all meals/snacks into an editable local draft. Show compact meal rows with pencil Edit actions, time/duration and kcal, expandable nutrient summary, final Save/Cancel. Edit shared meal/food controls locally with Apply/Cancel, fixed date/type/count, editable food composition, nutrients, portions, notes and timing. Preserve original times/durations/null times, notes, all foods; source stays unchanged. No meal writes until outer Save. Prompt before discarding dirty edits on source switch/navigation. Save all atomically and return to same dashboard date.
## Exact nutrients
Preserve calories, protein, carbohydrates, fat, vitamin D, total omega3, EPA+DHA, ALA, magnesium, fiber, salt, all portion references/quantities/units, provenance/estimate flags, fruit markers, zero vs null and saved aggregate values. No catalog lookup, estimation, nutrient derivation, or automatic recalculation during copy persistence. Intentional portion changes use existing scaling on/off behavior. Notes/name/time-only edits must not recompute nutrition. New persistence identities, MANUAL source, no ratings/day-completion/fasting/assessment copies.
## Interface and persistence
POST /api/meals/copy-day accepts {date: YYYY-MM-DD, meals: [complete editable meal snapshots without persistence IDs]}; snapshots use existing response field names (mealType, mealSequence, calories, proteinGrams, carbohydrateGrams, fatGrams, mealTime HH:mm:ss|null, durationMinutes, notes, dishes incl complete reference). Return existing RecordMutationResponse<List<MealResponse>>.
Use copy-specific DTOs in MealDtos.java with valid numeric/structural constraints allowing legacy unknown nutrient/reference values. Persist consumed and reference values exactly, not DishNutrition.apply. Shared user-row lock coordinates ordinary and Coach meal mutations; check empty target under lock; atomic all-or-none transaction; retain duplicates of snacks and reject duplicate fixed meal types. Reconcile automatic fasting/routines and personal records for complete result. No DB migration or Coach API changes.
